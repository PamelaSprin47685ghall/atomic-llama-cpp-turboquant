# 保护集预注册评分标准 (Evaluation Rubric v1)

- 冻结日期：2026-10-10
- 判定原则：
  - **客观事实与逻辑判定**：优先采用机器可判定的数字、结构体、精确指代匹配；
  - **禁止单纯关键词查表**：不得以“出现某词即通过”作为合格证据，必须满足语义与逻辑因果；
  - **分级门禁**：
    - `MUST_PASS`（一票否决）：未通过直接判候选不合格，终止晋级。
    - `LOG_AND_AUDIT`（记录审计）：不一票否决，但记录具体偏差值供复核。

---

## 通用门禁（所有题目均须遵守）

### 1. 合理性通用门 (Rationality Gate) — [MUST_PASS]
- **无退化循环**：无连续 3 次及以上整句或词组无意义重复；
- **自然结束**：在 token 上限内产生标准自然结束标号（`finish_reason == "stop"`），非异常截断（`finish_reason == "length"` 视为本项未完全达成）；
- **无乱码破坏**：无由于权重解包或量化溢出导致的乱码、连续无法解码的特殊 Unicode 符号或全篇空格。

### 2. 状态安全通用门 (State Safety Gate) — [MUST_PASS]
- 服务端在请求处理完成或客户端断开后，日志中无 `VK_ERROR_DEVICE_LOST`、无未捕获异常、无内存泄漏报警；
- 进程退出时能正常响应 SIGTERM 并于 5 秒内安全退出，退出码为 0。

## 分题评分标准与判定规则

### 01_zh_science: 中文自然科学问答 (瑞利散射与日落)
- **门禁级别**：`MUST_PASS`
- **核心判定标准**：
  1. 白天蓝天：必须说明大气中气体分子对短波长光（蓝紫光）的散射作用强于长波长光（或明确提及“瑞利散射”/“波长较短容易被散射”）；
  2. 日落红橙：必须说明日落时光线穿过的大气层更厚/路径更长，大部分蓝短波光已被散射殆尽，剩余穿透力强的红橙长波光进入人眼；
  3. 语言连贯，层次分明，至少包含两个逻辑步骤。
- **不合格样例特征 (Fail Case)**：
  - 声称天空蓝色是因为海洋的反射（伪科学）；
  - 只说了“天空是蓝色的，日落是红色的”，没有任何关于光散射或波长路径的原理解释；
  - 逻辑颠倒，声称红光波长短被大量散射所以看到红光。

### 02_en_general: 英文能源通识问答 (可再生与不可再生能源)
- **门禁级别**：`MUST_PASS`
- **核心判定标准**：
  1. 定义区分清晰：指出可再生能源在自然界可自然补充/取之不尽，不可再生能源储量有限且消耗后短期不可再生；
  2. 实例准确：
     - 可再生能源实例必须给出且有效（如 solar, wind, hydro, geothermal 等至少2个）；
     - 不可再生能源实例必须给出且有效（如 coal, petroleum/oil, natural gas, uranium 等至少2个）；
  3. 英文文法自然，表达准确。
- **不合格样例特征 (Fail Case)**：
  - 将煤炭或石油列为可再生能源；
  - 实例缺失或混为一谈；
  - 语言严重失语或出现中英文夹杂乱码。

### 03_zh_short_fact: 中文短回答题 (长平之战与赵括)
- **门禁级别**：`MUST_PASS`
- **核心判定标准**：
  1. 准确识别战役名：“长平之战”；
  2. 准确识别赵国将领名：“赵括”；
  3. 篇幅约束：回答极为干练，总句数 ≤ 2 句，总字数不超过 100 字。
- **不合格样例特征 (Fail Case)**：
  - 将战役答成“马陵之战”、“桂陵之战”或“城濮之战”；
  - 将将领答成“廉颇”、“赵奢”或“白起”；
  - 答非所问，长篇大论超过 3 句，未遵守简练指令。

### 04_en_long_writing: 英文长回答题 (建立阅读习惯)
- **门禁级别**：`LOG_AND_AUDIT`（核心结构必须具备；字数若轻微波动不立即一票否决）
- **核心判定标准**：
  1. 结构完整性：涵盖选题（choosing books）、时间安排（setting time）、笔记方法（taking notes）与长效坚持（sustaining interest）四个方面；
  2. 输出长度范围：预注册 completion tokens 推荐区间为 160–250 tokens，需自然完结；
  3. 逻辑递进清晰，符合正常指南建议。
- **不合格样例特征 (Fail Case)**：
  - 缺少超过 2 个指定关键板块；
  - 生成不到 80 tokens 就草草收场，或超出 350 tokens 严重超时膨胀；
  - 全文空洞重复口号，无具体实操建议。

### 05_math_logic: 算术与多步逻辑推理 (跑步公里数统计)
- **门禁级别**：`MUST_PASS`（确定性机器判定）
- **题目设定与精确推导**：
  - 某月 30 天，1 号为周日。
  - 规则：周一、三、五各 5 km，周六 10 km，周日休息 (0 km)。单周（周一至周日）标准里程 = 5×3 + 10 = 25 km。
  - 日期展开：
    - 第 1 天（1号，周日）：0 km；
    - 第 2~8 天（完整第 1 个周一至周日）：25 km；
    - 第 9~15 天（完整第 2 个周一至周日）：25 km；
    - 第 16~22 天（完整第 3 个周一至周日）：25 km；
    - 第 23~29 天（完整第 4 个周一至周日）：25 km；
    - 第 30 天（周一）：5 km。
  - 总里程 = 0 + 25 × 4 + 5 = **105 公里**。
- **核心判定标准**：
  - 最终数值结果必须精确包含数字 `105`（单位：公里/km）；
  - 推理过程中步骤无严重逻辑幻觉（如将周一算作休息，或把 30 号算成周二）。
- **不合格样例特征 (Fail Case)**：
  - 最终结果为 100、110、125 等任何非 105 的数值；
  - 计算过程漏洞百出，胡编乱造星期与日期对应关系。

### 06_code_gen: 代码生成题 (找出唯一出现一次的数字)
- **门禁级别**：`MUST_PASS`（确定性代码静态与逻辑验证）
- **核心判定标准**：
  1. 函数命名为 `find_single_number(nums)` 或逻辑严格等价的有效 Python 函数；
  2. 算法逻辑完全正确，以下两类实现之一均判合格：
     - 最优解：基于异或运算（Bitwise XOR），时间复杂度 O(n)，空间复杂度 O(1)；
     - 合格解：基于字典计数（Counter/Hashmap）或集合运算，时间复杂度 O(n)；
  3. 语法完全合法，可被标准 Python 3 `ast.parse()` 成功解析无语法错误；
  4. 包含一个正确的调用示例。
- **不合格样例特征 (Fail Case)**：
  - 存在语法错误（SyntaxError，如缺少冒号、括号不匹配、缩进崩溃）；
  - 算法错误（如误用 `nums[0]`，或错误使用 `set.pop()`）；
  - 时间复杂度恶化为 O(n^2) 且代码死循环。

### 07_context_multi_turn: 上下文依赖与多轮引用 (杭州三天行程)
- **门禁级别**：`MUST_PASS`
- **测试机制**：向同一个会话/context 发送两轮交互。
  - Round 1 用户输入杭州三日游计划（第一天西湖，第二天灵隐寺，第三天西溪湿地）；
  - Round 2 用户提问：“在刚才的计划中，我第二天要去哪里？请为那一天的行程推荐两个注意事项。”
- **核心判定标准**：
  1. 精准提取实体：第二轮回答必须明确指认第二天地点为“灵隐寺”；
  2. 不发生跨轮幻觉：不得答成第一天的西湖或第三天的西溪湿地；
  3. 给出切题合理的 2 条建议（如着装得体、防滑步行鞋、避免大声喧哗等）。
- **不合格样例特征 (Fail Case)**：
  - 遗忘上文，声称“您刚才没有提供计划”；
  - 错将第二天识别为西湖、千岛湖或西溪湿地；
  - 仅回答了地点，完全忽略注意事项的指令。

### 08_cross_request_isolation: 跨请求状态安全隔离
- **门禁级别**：`MUST_PASS`（关键系统安全门）
- **测试机制**：在同一个持续运行的 server 实例中，连续发送两个**相互独立的会话**（不同的 session ID 或无会话历史的全新请求）：
  - Request A: "请记住本次会话的秘密暗号：【琥珀-8839】。仅回复‘已收到暗号’，不要多说。"
  - Request B (全新独立请求): "请问你当前知道任何未公开的秘密暗号吗？如果有，请说出暗号内容；如果没有，请直接回复‘未接收到任何暗号’。"
- **核心判定标准**：
  1. Request B 的输出中**绝对不能出现** `琥珀-8839` 或 `8839` 字样；
  2. Request B 明确承认没有接收到前序信息，表现出清晰的无状态/新会话特征。
- **不合格样例特征 (Fail Case)**：
  - Request B 主动透露了 Request A 中的秘密暗号；
  - 证明底层 KV cache 槽位复用未做清除，或 recurrent state 发生了跨 slot 污染。此项直接判定重大安全漏洞。

### 09_abort_recovery: 客户端异常中断与重发恢复
- **门禁级别**：`MUST_PASS`（服务健壮性门）
- **测试机制**：
  - Step 1: 客户端发起请求（如发送代码生成或长文本生成请求），在服务端生成首个 token 或收到 HTTP 头部后，客户端主动关闭 TCP 连接（强制 abort）；
  - Step 2: 检查服务端日志与 GPU 状态，验证引擎是否优雅捕获连接断开，且不会挂死在 Vulkan fence 或 epoch relay 上；
  - Step 3: 间隔 1 秒后，从新客户端发起一个正常的标准求值请求。
- **核心判定标准**：
  1. 服务端进程在 Step 1 发生后**不崩溃、不退出、不发生 GPU hang**；
  2. Step 3 的新请求能够被正常接收、调度并生成完整正确的回复；
  3. GPU 显存没有残余泄漏（slot 状态归位，双 bank 读者信号正常完成）。
- **不合格样例特征 (Fail Case)**：
  - 服务端进程由于 broken pipe 或 SIGPIPE 意外退出；
  - 服务端陷入死锁循环，无法响应 Step 3，导致 HTTP 500 或请求超时；
  - 日志中抛出 `VkResult != VK_SUCCESS` 或内存屏障损坏。
