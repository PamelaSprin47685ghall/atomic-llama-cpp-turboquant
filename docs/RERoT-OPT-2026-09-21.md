## 1. 使命与基线定位

### 1.1 核心使命
本台账规定 RERoT（Recursive Episodic Reasoning over Tree/DAG）在当前代码库中的性能调优与稳定性加固实施路线。优化目标是释放单卡与异构执行环境下的并发 DAG 解码潜力（尤其是 Navi 21 / AMD RX 6800 上以 $P = 6$ 最优笔容量执行多 Lane 拓扑时的吞吐与确定性），而不是重新发明一套并发调度理论。

### 1.2 边界与定位铁律
1. **彻底避开 TP5 走过的弯路**：
   - 不搞过度设计与脆弱状态机（不凭空捏造胶水转换层与两套工作机制）；
   - 杜绝无界自旋与无保护设备轮询，绝不破坏驱动与硬件看门狗的安全底线；
   - 严禁制造“第二套真相”（禁止私设不透明缓存或与调度器脱节的影子数据结构）；
   - 坚决落实“写了测试不等于跑过测试，读过代码不等于构建通过”的纪律；
   - 严禁假门禁与假断言，杜绝靠放宽断言、跳过报错或删除证据制造表面上的通过。
2. **非新架构，不搬旧分支**：
   - 本程序属于 RERoT 现有 DAG 执行语义与资源模型内部的确定性收敛与开销消除；
   - **绝不是**引入新的模型图执行架构；
   - **绝不**将五卡 TP5 分支、RELAY 专属机制或多卡通信协议生搬硬套至本台账覆盖的单卡/原生 RERoT 执行流。
3. **基线冻结**：
   - 严格以 `HEAD 2e4bb881b` 为事实起点。任何历史提交、旧分支经验或旧文档推论，未在此基线上重新核实前，均不得作为生效依据。

## 3. 测量协议与性能评估规范

为避免落入虚假收益与测量噪声陷阱，所有性能验证必须严格执行以下测量协议：

### 3.1 三组严格对照实验
任何性能对比必须同时测量并汇报以下三组对照：
1. **当前基线 vs 候选补丁**（Current HEAD `2e4bb881b` vs Candidate Patch）：在相同编译选项、相同软硬件环境下的配对对比。
2. **同 RERoT 架构下变参对照**（Same RERoT Varying $P$ / Batch Size）：在固定优化代码下，对比 $P=1, 2, 4, 6$ 以及不同批处理切片规模的线性度与开销变化。
3. **RERoT ON vs 单流 (Single-Stream) OFF 对照**：测量并发 DAG 启用状态与完全关闭 RERoT、仅走原生串行单流基线时的端到端吞吐与端到端延迟对比。

### 3.2 细粒度请求分账
禁止使用单一的“总吞吐”或“平均耗时”掩盖内部开销。必须对每个请求进行阶段分账：
- **Prompt Prefill 耗时**（ms 与 tok/s）；
- **Strategy Probe 耗时**（ms，含探测开销与 $C_0$ 状态保存/恢复耗时）；
- **Multi-Lane DAG 并发解码耗时**（各活跃 Lane 的并行 decode 耗时、同步等待空泡、拓扑依赖阻塞耗时）；
- **Synthesis 综合阶段耗时**（固定 View 后的生成耗时）；
- **系统/调度开销**（命令录制、队列提交、内存屏障与显式等待时间）。

### 3.3 成对 A/B/B/A 测试模式与全样本报告
- 测试序列必须严格按照 **A $\to$ B $\to$ B $\to$ A**（或交替循环）执行，以抵消热机、温度漂移、功耗墙抖动和缓存冷热态干扰；
- **禁止仅汇报平均值**：必须完整报告每个独立样本值、中位数（Median）以及四分位距（IQR）；严禁用均值抹平偶发长尾或同步悬挂。

### 3.4 5% 中位数建议门及其非统计定律性质
- 引入 **5% 中位数改进阈值** 作为补丁是否具备性能推进价值的工程建议门槛：候选方案相对于基线的中位数性能提升需 $\ge 5\%$，且不伴随长尾退化；
- **声明其非统计定律属性**：5% 仅是工程过滤启发式规则，不是自然界或统计学绝对铁律。绝不能将测量误差范围内的轻微波动硬套为“5% 显著收益”，更不能在未满足安全门与正确性断言时，借口“中位数提升了 5%”而强行放行。

### 3.5 观察器扰动配对验证 (Observer Perturbation Verification)
- 任何用于采样的 Profiler、Tracer、日志打印或系统调用拦截（如 strace/ftrace），必须先进行侵入性扰动评估；
- 必须对比“开启观察器”与“纯净运行（无侵入测量）”的性能基线差异；
- 严禁在带高开销追踪器的环境下直接采集对外宣称的生产吞吐数字。

### 3.6 双通道观测裁定：生产通道与诊断通道
关于性能采样与运行观测，确立双通道独立运行原则：
1. **通道职责界定**：
   - **生产通道 (`server_rerot_metrics`)**：面向服务端常态部署与轻量指标暴露，负责统计吞吐、请求生命周期与全局队列健康度，以零分配、零日志侵入为前提。
   - **诊断通道 (`llama-rerot-profile`)**：面向工程调试、算法剖析与细粒度阶段耗时分解（支持微秒级时间戳、环形缓冲事件溯源与路由拒绝计数），通过开关受控启用。
2. **同站点双计时、不互相派生**：
   - 生产通道与诊断通道在相同的观测站点（如 prefill 完成、DAG 分叉、frontier 推进、synthesis 启动）各自独立采集原始单调时钟与计数；
   - **严禁数据派生**：生产通道不得读取诊断通道的内存结构，诊断通道亦不得改写或派生生产通道数据；
   - 确保即使诊断通道完全关闭、剥离或发生故障，生产通道仍能保持绝对确定性与零开销运行，杜绝跨通道数据耦合。

## 5. 回归测试规则

### 5.1 构造原则：旧行为必红
每个单独交付的补丁必须伴随一道或多道自动化回归测试，且必须满足以下铁律：
1. **从真实 incident 出发**：测试用例必须精准复刻既往故障、死锁、内存越界、竞争条件或数值漂移的真实触发场景；
2. **经由真实 owning boundary 进入**：测试必须从实际持有该职责的公开接口或边界类调用，严禁侵入组件私有实现去人工修改内部标志绕过真实执行路径；
3. **断言 caller-visible 最终结果**：断言必须落在调用方可感知的最终输出、状态码、返回数据或设备事件上，而不是断言某行内部代码是否被执行；
4. **历史版本可证伪性**：该测试在旧代码（未打入本补丁时）上运行必须确定性地触发失败（变红），在合入本补丁后必须确定性地通过（变绿）。

### 5.2 禁止事项
- 严禁通过放宽误差范围（如增大容差 epsilon）、注释断言语句或将 fatal error 降级为 warning 来制造绿灯；
- 严禁测试中依赖未初始化的全局状态或外部未受控的网络/文件副作用。

## 7. 关键裁定记录（Architecture Decision Records, ADR）

本节记录本轮 RERoT 优化与工程治理中的核心架构决策。每条裁定均明确阐释背景与约束、选定路径、可信替代方案、拒绝理由、系统后果以及触发重新审视（revisit）的新证据条件。

### ADR-01: 双通道观测体系裁定（生产通道常开与诊断通道环境门控）
- **背景与约束 (Context & Constraints)**：RERoT 执行流包含动态 DAG 调度、探测回滚、多 Lane 前缀重构与跨 reader KV 共享，既需要对外稳定输出标准监控指标，又需要在深度调优时获取微秒级事件与内部命中细节。观测逻辑绝不能在热路径上引入动态内存分配，不得产生每 token 日志污染；同时，系统存在明确的分层铁律：底层 `ggml` 算子库绝对不得反向依赖应用层 `src/`。
- **选定路径 (Chosen Path)**：
  - **生产通道 (`server_rerot_metrics`)**：生产环境中常态开启，提供零动态分配、零日志侵入的指标聚合，接入服务端 `/metrics` 监控端点，并在 API 响应中暴露 `usage.rerot` 可选键；
  - **诊断通道 (`llama-rerot-profile`)**：通过 `LLAMA_REROT_PROFILE` 环境变量门控开启，提供富字段追踪、纳秒级时间戳以及编译期固定的 256 项深度环形缓冲（ring buffer）；
  - **算子层计数器归属**：所有 ggml 内部的底层执行计数（如 Vulkan RERoT 专用 kernel 派发、共享显存 shmem 拒绝等）统一归入 `ggml_tp5_profile`，由图计算入口激活与统计；
  - **同站点独立采集、不互相派生**：两大通道在相同业务站点（如 prefill 完成、DAG 分叉、frontier 推进、synthesis 切换等）各自直接读取单调时钟与计数，严禁跨通道读取内部变量或相互派生。
- **可信替代方案 (Credible Alternatives)**：
  - 采用单一大一统 profiler，由一套跨层结构统管图构建、执行与请求生命周期的全部数据采集。
- **拒绝理由 (Rejection Rationale)**：
  - 三层的激活窗口与归属截然不同（图构建期、图执行期与请求生命周期）；
  - 单一结构会强行破坏 `ggml` 不得依赖 `src/` 的分层铁律，且会将重型追踪开销带入生产热路径。
- **后果 (Consequences)**：
  - 生产通道保持绝对轻量与确定性，诊断通道可在免受生产干扰的前提下独立深度剖析；
  - 双通道各自直读时钟，需要维护两套独立的打点站点代码。
- **Revisit 触发条件 (What New Evidence Triggers Revisit)**：
  - 若真机高并发压测实测证明同站点双直读时钟对 CPU 关键路径引入超过 0.5% 的可测开销；或出现新型跨层零拷贝硬件追踪基础设施。

### ADR-02: P2 补丁（融合 Q-prep 新算子）押后决策
- **背景与约束 (Context & Constraints)**：讨论稿 §16 规划了 P2 融合算子，拟将 gather、RoPE 与 live count 校验融合成单一 kernel 以规避 padding 浪费。但在当前架构下，P1 补丁引入的小 group 桶（容量设为 32）已通过离散桶化消除了绝大部分跨 group 填充浪费。
- **选定路径 (Chosen Path)**：
  - 明确押后 P2 补丁的开发与合入，当前继续沿用标准算子链路；
  - 维持观察状态，等待 P0 的 live/cap 计数器采集到真实运行基线。
- **可信替代方案 (Credible Alternatives)**：
  - 立即启动针对 CPU（AVX2/NEON）与 Vulkan（GLSL/SPIR-V）的双实现 Q-prep 融合新算子研发。
- **拒绝理由 (Rejection Rationale)**：
  - P1 小 group 桶（32）已解决了大部分填充浪费问题；
  - 在 P0 live/cap 计数尚未给出确凿数据前，无法证明桶内残余 padding 是显著性能瓶颈；为极少量的残余 padding 同时开发、维护并验证 CPU 与 Vulkan 双实现新算子，付出的工程复杂度与数值漂移风险远超预期收益，违背“先查清再动手”与反过度设计的纪律。
- **后果 (Consequences)**：
  - 避免在缺乏数据支撑时引入复杂的双后端算子实现与维护包袱；
  - 保留了算子层的简单性与高可移植性。
- **Revisit 触发条件 (What New Evidence Triggers Revisit)**：
  - 当 P0 无扰动基线运行数据明确显示 Q-prep 阶段耗时占 decode 整体的可测显著份额，且桶内残余 padding 浪费经测量确证为关键瓶颈时。

### ADR-03: P11 补丁（9469 同步去重与 clear 事务复用）押后及 2355 同步安全底线
- **背景与约束 (Context & Constraints)**：P11 提议清理 `server_context.cpp` 第 9469 行的同步检查并事务化 clear 代伦复用。然而在 2026-09-21 刚刚发生过多 Pen ($P=6$) 异步命令竞争触发 `radv: GPUVM fault detected ... ErrorDeviceLost` 的严重事故，排查证明 `server-context.cpp` 第 2355 行处的前缀重构同步（`llama_synchronize(ctx_tgt)`）以及 `llama-memory-recurrent` 的清空同步是防止破坏性显存重置踩踏前向计算命令的救命防线。
- **选定路径 (Chosen Path)**：
  - 押后 P11 的去重与代伦复用改动；
  - 9469 行处的同步去重决策必须等待已落盘的 `sync_sample_no_work` 与 `sync_sample_with_work` 计数器提供真实计时证据，证明第二次同步确实存在且不是快速返回；
  - 2355 行处的前缀重构同步与 `llama-memory-recurrent` 同步被定为系统的绝对安全底线，**任何后续优化一律禁止撤销**。
- **可信替代方案 (Credible Alternatives)**：
  - 直接在源码中删除 9469 行与 2355 行的显式 `llama_synchronize` 调用以消除 CPU/GPU 同步泡。
- **拒绝理由 (Rejection Rationale)**：
  - 撤销 2355 行与 memory-recurrent 同步会直接重蹈 09-21 异步命令竞争的覆辙，再次诱发 `ErrorDeviceLost` 与硬件看门狗崩溃；
  - 在未获得 `sync_sample_no_work/with_work` 真实分布前，主观推测 9469 行冗余属于无凭据改动。
- **后果 (Consequences)**：
  - 绝对守住了驱动与整机不挂起、无 GPUVM fault 的硬件安全底线；
  - 多 Pen ($P=6$) 运行保持百分之百确定性。
- **Revisit 触发条件 (What New Evidence Triggers Revisit)**：
  - 仅当真实运行计时数据证明 9469 行处第二次同步消耗了显著非零的真实等待时间（而非零开销快速返回），且有证明显示其前置因果已被完全覆盖时，方可评估去重；2355 与 memory-recurrent 安全底线则不可撤销。

### ADR-04: 构建串行链与单写者规则 (Single-Writer Rule & Build Serialization)
- **背景与约束 (Context & Constraints)**：在多分道（lanes）并发推进时，若不同实现分道并发写入相同源码文件（例如 `llama-graph.h`、`server-context.cpp`），极易引起内容互相覆盖与逻辑撕裂；同时，若在代码正在被编辑的中间状态下触发构建，会导致误导性的虚假编译失败。
- **选定路径 (Chosen Path)**：
  - **单写者规则**：同一文件物理区域在同一时间段内严格只允许一个实现 lane 进行写入；后续依赖修改必须通过工作交接与 resume 机制串行接续推进；
  - **构建串行链**：全量构建必须在工作树内完全没有源码写者、所有源码修改彻底落盘后方可执行。
- **可信替代方案 (Credible Alternatives)**：
  - 允许多个 lane 同时并发编辑相同文件，或在单 lane 编辑途中随时触发后台构建进行即时验证。
- **拒绝理由 (Rejection Rationale)**：
  - 并发写入同一文件必然导致修改被互相覆盖，造成工作成果静默丢失；
  - mid-edit 构建产生的语法错误与依赖缺失会制造大量无效报错干扰，浪费宝贵算力并破坏问题定界。
- **后果 (Consequences)**：
  - 彻底杜绝了代码覆盖与构建噪声，保证了代码提交历史与变更集的可追溯性；
  - 流程上需要严格遵守“写完 $\to$ 冻结 $\to$ 统一构建验证”的纪律。
- **Revisit 触发条件 (What New Evidence Triggers Revisit)**：
  - 当项目完成物理架构重构，所有子模块完全拆分至互不重叠的独立代码目录与独立目标时。

### ADR-05: P4 补丁（frontier 增量索引与事务发布）押后决策
- **背景与约束 (Context & Constraints)**：P4 旨在实现增量 frontier 索引与 $W > P$ 事务发布机制，以优化高并发工作线程下的调度可见性。但该机制在底层深度依赖 P3（batch 内共享 cell 元数据与 run 索引），而 P3 的改动涉及复杂的 KV cache 底层寻址，对全序列解码正确性具有极高风险。
- **选定路径 (Chosen Path)**：
  - 严格押后 P4 补丁；
  - 绝不在未经构建与回归测试充分验证的 P3 基础之上叠加 P4 的 $W > P$ 事务发布逻辑。
- **可信替代方案 (Credible Alternatives)**：
  - 在 P3 刚落盘但未经编译测试的状态下，立即并发铺开 P4 事务发布逻辑的实现。
- **拒绝理由 (Rejection Rationale)**：
  - P3 属于核心内存视图抽象，其潜在的越界或元数据竞争风险若未先行排除，叠加上 P4 复杂的增量事务后，一旦出现数值不一致或死锁，将根本无法定界根因所在；全序列正确性是不可妥协的红线。
- **后果 (Consequences)**：
  - 避免了高风险逻辑的多重叠加，确保每一步推进都踩在坚实验证过的基础之上。
- **Revisit 触发条件 (What New Evidence Triggers Revisit)**：
  - 必须等待 P3 经过全量编译，且配套的 `test-rerot-view` 差分测试全量变绿（100% PASS）确认无任何元数据异常后，方可解冻 P4。

### ADR-06: 机器硬件占用与非侵入等待决策 (Hardware Occupancy Non-Intrusive Wait)
- **背景与约束 (Context & Constraints)**：目标真机当前正运行用户所属的 `llama-server` 生产/实验实例（PID `705682`，运行模型 Bonsai-27B RERoT $P=6$，占用显存约 15.64 GiB）。
- **选定路径 (Chosen Path)**：
  - 明确将我方所有真机基线测量、GPU 压测及性能门禁置为**完全阻塞（Blocked）**状态；
  - 严格等待该外部进程自然结束并释放资源，中途保持绝对只读观察；
  - **严禁**任何形式的主动杀进程（`kill`/`pkill`）、显卡抢占或重置他人运行状态的行为。
- **可信替代方案 (Credible Alternatives)**：
  - 强制终止 PID `705682` 进程以立刻释放显存；或在剩余的显存空间内强行压入测试实例。
- **拒绝理由 (Rejection Rationale)**：
  - 强行杀死他人正在运行的关键进程是对系统协作底线的破坏，属于严重事故；
  - 在已被大量占用的显存上叠加 GPU 负载会直接导致显存超额、触发驱动层 OOM 或导致内核级硬件挂起与重启；由此采集出的任何数据也全无基准对比价值。
- **后果 (Consequences)**：
  - 确保了整机安全与他人工作的连续性；
  - GPU 测量阶段必须顺延至外部机器资源完全释放之后。
- **Revisit 触发条件 (What New Evidence Triggers Revisit)**：
  - 外部进程 PID `705682` 自然退出，且经由 `scripts/gpu-idle-audit.sh` 审计确认 GPU 显存完全回落至空闲基线（`gpu_busy = 0%`）时，阻塞自动解除。

### ADR-07: PQ2_0 融合拒绝裁定 (PQ2_0 Fusion Rejection Ruling)
- **背景与约束 (Context & Constraints)**：Bonsai-2-27B-PQ2_0 模型的投影权重为 PQ2_0 量化类型，而当前 TP5 融合匹配器仅识别并支持 Q5_K/Q6_K 组合。
- **选定路径 (Chosen Path)**：维持类型守卫，走标准分立 `mul_mat` 分发回退路径，并将拒绝原因 schema 化写入 `ggml_tp5_profile` 观测系统。
- **可信替代方案 (Credible Alternatives)**：硬接融合 shader：引入新的 SPIR-V 变体、手写 `calc_superblock_pq2_0` 反量化逻辑、补齐 MMVQ 支持，并对融合匹配器及 22719 输出投影执行全套改造。
- **拒绝理由 (Rejection Rationale)**：
  - SPIR-V 变体膨胀与长期维护成本过高；
  - 手写复杂的底层反量化与 MMVQ 在 Navi 21 上存在极高的 GPU 故障（如 VM fault / ErrorDeviceLost）风险与数值漂移隐患；
  - 四投影融合在整体解码耗时中的边际收益完全无法抵消引入的系统脆弱性与开发维护负担（收益不抵）。
- **后果 (Consequences)**：四投影融合拆为分立 dispatch 带来少量的额外派发开销，但换取了确定性的数值正确性、内核稳定性与整机硬件安全。
- **Revisit 触发条件 (What New Evidence Triggers Revisit)**：仅当 P0 细粒度归因分析明确显示 PQ2_0 投影为可测显著热点，且标准分立通路被实测确认为吞吐瓶颈时，方可重新评估融合支持。
