  The probe records the predicate at the op-dispatch case of ggml-cuda.cu, where the node is

      flag on,  src[5] i32[2]   enabled=1 active=0                          (not a scalar: declines)
  So the guard's predicate computes exactly what LIMITS.md §3a says it should, and it is the
  identity of src[5] — flags/buffer/size — that decides it.

4) WHAT IS NOT ESTABLISHED (stated because the matrix cannot show it)
---------------------------------------------------------------------
  * The abort itself was not observed: ggml_cuda_flash_attn_ext was reached in the probe build but
    launch_fattn (the R2 site) was not entered for these nodes in this harness, so the "abort with
    canary intact" claim has no direct witness here. What is witnessed is the predicate that guards
    it (ingraph=1 for a view-bound src[5], 0 for the legal one) and the source order in the patch
    (R2 sits at the head of launch_fattn, before any K/V work — G1 asserts that order statically).
  * The vector case shows a real limit of the design, not a build problem: ggml_cuda_fattn_rtlen_tensor()
    returns null for anything but i32[1], so the guard's predicate declines and the node runs
    unguarded. That matches LIMITS.md §3a condition 3 (the guard protects only nodes that carry an
    i32[1] src[5]); it means "not a scalar" is a case the launch boundary cannot refuse, because it
    never becomes active for it.
  * The relay's R1 (submit) path was not exercised: it needs the relay provider with captured stage
    graphs, which this harness does not build.
