2) HARNESS DEFECT FOUND AND FIXED (the earlier FAIL cause)
----------------------------------------------------------
  The first harness sized its float source buffer as HD*LO = 3,276,800 floats and then
  quantized three different weight shapes from it, the largest being E*HD = 26,214,400
  floats (chain 2560x10240). ggml_quantize_chunk reads nrows*n_per_row floats, so it read
  ~92 MB past the end of the vector: the fault address was always a page boundary and the
  outcome depended on what the allocator happened to map there, which is why identical
  commands alternated between success and SIGSEGV. Fix: every quantize call now gets a
  source of exactly n0*n1 floats and a destination of ggml_row_size(Q8_0, n0)*n1 bytes,
  both checked (n0 % 32 == 0, f.size() == n0*n1, written == needed) before the call
  (m3rows-micro.cpp, quantize_checked). After the fix: 8/8 identical invocations rc=0, and
  all G3 legs below ran three times without a single fault.

    variant                                            on kernels   why=0   bytes

    gate fed by a constant instead of up                   8         0           0
    up forced to zero                                      9         0           0
    epilogue reads x0 instead of xn                        5         4      15,338
  So the fused site is admitted exactly when nothing else reads `up`, and in that case the
  site's mixed output differs from the generic chain by max 2.6e-2, mean 3.5e-3, rel L2
  3.2e-2 at R=1..4 — deterministic across runs (two identical ON legs, 0 bytes apart) and
  identical in every row of the R-row legs. The row kernel's lo and up are not bitwise the
  generic chain's either (up maxabs 0.22 in the same probe); the epilogue is not involved,
  because forcing the gate constant and reading a fixed xn gives 0 bytes.

  the model actually takes, and that path changes values far beyond ulp range. The model
